# update21：换上新的倒奶模型（测量入口）后重新拟合 —— 郁金香打开了吗？（N = 256）

## 要回答的问题
倒奶模型改了（下一节）。用新的倒奶模型重新拟合参数以后：
1. **物理模型 S1kq** 能不能打开郁金香？
2. **基线 v05n** 能不能打开？
3. 如果打开了，是**新入口**的功劳，还是 **pose v2 + 重新拟合**本身就够了？（对照试验回答）

还是用视频反传（精确伴随梯度 + Adam），只用 tulip + leaf 训练；heart、push_heart、swan 留出，只报告。

## 倒奶模型改了什么（一段话）
以前的倒奶模型让奶沿壶嘴唇边的“法线”方向流出，出口速度 = √(2gH)（没有标定；bp256_trained 和 S1kq 都是在它上面拟合的，对照试验也用它）；曾经试过的标定 EXIT_CAL 现在也不用。结果奶柱落到液面时的水平速度只有实测的一半不到（低位倒奶时约 0.11 m/s，视频里量到约 0.25 m/s），竖直速度又偏大（约 0.62 m/s，实测约 0.52 m/s）。新的倒奶模型（“测量入口”，MI）前面几步完全不变：拉花缸位姿（pose v2）、壶的 CAD 几何、液面、用堰流公式算流量。改的是出口和飞行：奶沿着壶的**内壁切向**流出，出口速度由**动量守恒**算（宽顶堰临界断面 + 粘性边界层修正，参数都是独立估计的，没有拟合），飞行按**带表面张力的圆柱射流**算（是替换，不是叠加）。在 tulip 和 leaf 视频能量到奶柱的时段（“测量窗口”：tulip 0–1.70 s 和 3.38–4.14 s，leaf 0–4.12 s），落到液面的水平速度、竖直速度、飞行时间再换成**实测值**（平滑后），落点放到验证过的奶柱落点上（MI-R；只用通过帧门的帧的落点）。窗口外的流速和飞行就是出口定律的，落点则带着从窗口内落点取来的一个常数平移（N 96 实测 tulip 约 1.9 mm、leaf 约 1.1 mm）；三杯留出用只有出口定律的版本（MI-L，E0 关）。流量还是堰流公式的，开流时刻不变。注意：出口**方向**是假设的规则，没被测量检验；定律在标定数据上只是勉强通过，所以 MI 标为“暂定”。

## 入口修正盒（4–7 用；每 0.2 s 一个节点，节点之间线性插值）
每个界限是每个节点的 2σ。在测量窗口内，σ = 测量带（GP）⊕ 系统误差 ⊕ 结构项；窗口外（只有定律的帧：高位倒奶、空档）是**定律在标定数据上的散布**，不是测量误差。

| 量 | 测量窗口内 | 只有定律的帧 | 'meas_wide' |
|---|---|---|---|
| 落点 dx、dy | ±4 mm | ±4 mm | ±10 mm |
| 流量倍率 | ×0.5–2 | ×0.5–2 | ×0.2–5 |
| 竖直到达速度 U_perp | 测量带 2σ（约 ×1.16–1.20） | ×1.19 | 半宽 ×2.5（约 ×1.5） |
| 水平到达速度 u_h | 测量带 2σ（约 ±0.09–0.10 m/s） | ±0.10 m/s | 约 ±0.25 m/s |
| 图案阶段总奶量 | ×0.8–1.25 | | ×0.5–2 |

- 'meas' **不包括**“奶柱是直的、更快”的读法（R1 那种 +0.15 到 +0.3 m/s）；oracle 要这么多，是盒子决定的，不是关于 R1 的证据。
- 和 diag256 的盒子不一样（落点 ±4 vs ±8 mm，U ×1.19 vs ×1.4，du 都是 ±0.10 m/s），pose 也换成了 v2，所以 4–7 不能直接和 diag256 的 B–D 比。

## 运行
把 `diag21_patch.tar.gz` 上传到 `/root/autodl-tmp/`，在已有的 u20 基础上建一个新目录（不用重传整个包）：

```bash
cd /root/autodl-tmp && rm -rf u21 && mkdir u21 && cd u20 && cp -r latte_imex raw_data fonts scripts closures ../u21/ \
  && tar xzf /root/autodl-tmp/diag21_patch.tar.gz -C /root/autodl-tmp/u21 \
  && cd /root/autodl-tmp/u21 && bash scripts/autodl_diag21.sh
```

- 命令在后台启动，前台多等一会儿（约 45 分钟，最多 90 分钟），把开头的检查一条条报给你：
  1. 文件校验（`MANIFEST.sha256`）、环境、冻结输入（pose v2 的位姿文件、测量入口文件、起点参数，都按 sha256 核对）；
  2. 两个梯度自检（CPU，N 32，1 秒）：旧入口一个，新入口 + S1kq 的四个参数一个；不过就停，请把 `results_diag21/selftest_gradcheck_*.txt` 发我；
  3. SMOKE：七个试验各在 N 32 上跑 1 次迭代（GPU），把整条流程走一遍；哪个失败，那个试验之后会被跳过（日志里有 WARNING，`FORCE=1` 可强制跑）；
  4. 计时：S1kq 和 v05n（都用新入口）在 N 256 上各跑 2 次迭代（约 10 分钟），按两者的速度比给 S1kq 定时间槽（让它和 v05n 的同类试验迭代次数差不多，最多 2.5 小时）。
  
  看到“start-up checks done”就可以关掉终端。看进度：`tail -f /root/autodl-tmp/u21/results_diag21/diag21.log`；每个试验的逐次迭代在 `results_diag21/<模型>/<模式>.log`。
- **GPU 被别的任务占着时会自动等**（每 2 分钟看一次，最多 `MAXWAIT_H=3` 小时），空了再开始计时；不想等加 `NOWAIT=1`。梯度自检在 CPU 上，等 GPU 之前就先做。
- 中断后接着跑，用这一行（**不要**再执行上面那一整段：它开头的 `rm -rf u21` 会删掉所有结果和断点）：

  ```bash
  cd /root/autodl-tmp/u21 && bash scripts/autodl_diag21.sh
  ```

  做完的检查和试验跳过，没跑完的从断点（`state.npz`）接着跑；如果后台那一次还在跑，它会提示“a run is still working”并退出。某个试验没写出 `done.json` 会自动重试一次（从断点接着跑，用这个试验剩下的时间；如果拟合已经结束，只重做出图）；每个试验有硬时限，卡住不会拖累后面的。

## 时间
- 总预算 `BUDGET_H=15` 小时（从 GPU 空出来算起）。开头检查约 0.75 小时。
- 每个试验约 2 小时：拟合 1.35 小时（params）/ 1.6 小时（其余），N 256 每次迭代约 90 秒（diag256 在 4090 上实测，旧入口，两杯并行；新入口帧数少约 1/3，可能更快），即约 55–65 次迭代，最多 `ITERS=80` 次；最后 0.3 小时出图、出视频；params 再加 0.3 小时跑留出三杯，1、2 再加约 0.2 小时跑桥。S1kq 的时间槽按开头的两次计时（S1kq / v05n 的速度比）调整。
- 顺序就是上表：**提前停也能拿到前面的答案**——约 3 小时后有 S1kq params 的结果，约 5 小时后有 v05n params，约 7 小时后有对照。时间不够时，前面的试验保持计划的时长，压缩的是后面的；预算用完以后剩下的试验每个只拟合 0.25 小时（再加出图），所以 `BUDGET_H` 是软上限：调低到 8 小时，前三个仍各有约 1.35 小时，后面的 oracle 试验被压到 0.25 小时，总时长约 10 小时。
- 一次只跑一个试验（24 GB 显存放不下两个，diag256 实测峰值 19.2 GB）。

## 须知
- **oracle 只作诊断。** 4–7 的入口修正是用视频反推的，违反“手的动作是测量值、不能用图案去改”的原则，所以：它不会变成入口，不会进模型参数（4–7 的 `best_closure.json` 里没有入口字段），也不用来在不同的测量读数之间裁决（包括 R1）；最多说明哪些独立测量值得做。“在测量 2σ 以内”只在测量窗口里读。
- 新倒奶模型是**暂定**的：出口方向是假设的规则，定律在标定数据上勉强通过；留出三杯用的 MI-L 尤其如此（heart 上定律可能偏快 0.1 m/s）。
- S1kq 的起点里，τ_s = 0.0348 s 是从视频偏移换算来的起点（F(t)），在 params 里放开，在 inlet 里固定；B_dep 1267 仍在新入口下的独立范围内（C）；κ_Q 2.06 不变（F(t)）。
- 只用 tulip 和 leaf 训练；留出三杯只报告，从不参与任何选择。
- 入口改动图要看**有梯度的地方**；其余节点因为先验，基本留在测量值。日志里每次迭代的 `scan` 是“相邻两帧落点移动的最大值 / 求解器步长上限”。在 N 256 上，还没有任何修正的起始值就大于 1：新入口（MI-R）tulip 约 5.8、leaf 约 5.6（99% 的帧在 3 以下），旧入口 R1 约 10.7 / 7.6（diag256 第 0 次迭代打印的是 7.0 / 8.8）。所以 4–7 的 oracle 试验一开始就会打印 5–6，这是正常的；只有它在拟合中明显超过本试验第 0 次迭代的值（比如翻倍）才请告诉我。
